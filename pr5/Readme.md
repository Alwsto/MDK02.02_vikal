# ПР5 — Git Flow для АИС «Управление студенческой нагрузкой»

## Модель ветвления

Используется упрощённый Git Flow:

- `main` содержит проверенные версии, пригодные к выпуску;
- `develop` — общая интеграционная ветка текущего цикла разработки;
- `feature/<issue>-<short-name>` создаётся от `develop` для одной задачи;
- `release/<version>` при необходимости готовит согласованный выпуск от `develop`;
- `hotfix/<issue>-<short-name>` создаётся от `main` для срочного исправления и после проверки попадает в `main` и `develop`.

Примеры: `feature/42-load-report`, `bugfix/57-plan-validation`, `release/1.0.0`, `hotfix/63-auth-token-expiry`.

Для небольшой учебной команды `release/*` и `hotfix/*` используются только при необходимости. В обычной работе разработчики не коммитят напрямую в `main` или `develop`.

## Жизненный цикл задачи

1. В GitHub создаётся Issue с описанием результата и критериями приёмки.
2. Разработчик назначает задачу себе и создаёт ветку от актуальной `develop`.
3. Работа выполняется небольшими логическими коммитами. Рекомендуемый формат: `feat: add workload summary` или `fix: validate plan hours`.
4. Разработчик синхронизирует ветку с `develop`, запускает проверки проекта и открывает Draft PR в `develop`, связывая его с Issue.
5. После готовности PR переводится в обычный режим. Автор отвечает на замечания и обновляет ветку.
6. Tech Lead проверяет изменения и даёт одобрение. Обязательные CI-проверки должны пройти успешно.
7. PR сливается через GitHub с использованием Squash and merge; ветка задачи удаляется.
8. В конце цикла согласованные изменения из `develop` попадают в `main` через `release/*`. Срочные исправления проходят через `hotfix/*` и возвращаются также в `develop`.

## Роли

- **Developer** уточняет задачу, работает в отдельной ветке, добавляет или обновляет проверки, открывает PR и устраняет замечания.
- **Tech Lead** проверяет соответствие требованиям, архитектурные границы, безопасность и читаемость изменений; одобряет слияние или запрашивает правки.
- **Автор PR** не одобряет собственный PR. Для небольших учебных команд второй участник может выполнять роль Tech Lead по очереди.

## Code Review

Проверяющий оценивает соответствие критериям Issue; влияние на сценарии формирования учебных планов, расчёта часов, отчётности и авторизации; корректность валидации и обработки ошибок; безопасность и отсутствие секретов; понятность кода и документации; наличие уместных тестов и успешных CI-проверок. Замечания должны быть конкретными и объяснять ожидаемое изменение. PR не сливается с неразрешёнными блокирующими замечаниями.

Файлы `.github/` в этом каталоге можно перенести в корень репозитория GitHub, а `CONTRIBUTING.md` — в корень репозитория.
