# Регламент разработки

## Ветки и задачи

- `main` хранит проверенное состояние проекта, `develop` — общую ветку интеграции.
- Рабочие ветки создаются от актуальной `develop`: `feature/<issue>-<short-name>` или `bugfix/<issue>-<short-name>`.
- Срочные исправления выпущенной версии создаются как `hotfix/<issue>-<short-name>` от `main` и после слияния переносятся в `develop`.
- Один Issue и один Pull Request должны описывать согласованный объём изменения.

## Pull Request и ревью

PR направляется в `develop`, связывается с Issue и содержит краткое описание, способ проверки и затронутые части системы. Автор PR не одобряет собственную работу. Слияние разрешается после одобрения Tech Lead или назначенного проверяющего, успешных обязательных проверок и устранения блокирующих замечаний. Рекомендуется Squash and merge и удаление рабочей ветки после слияния.

## Актуализация артефактов

Изменение API обновляет OpenAPI и клиента; изменение зависимостей обновляет архитектурное описание и при необходимости ADR; изменение командных правил обновляет этот файл. Не добавлять в коммиты реальные пароли, токены и персональные данные.
